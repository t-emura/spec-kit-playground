# Feature Specification: ファイルベースのデータ保存

**Feature Branch**: `006-file-based-storage`  
**Created**: 2026-03-31  
**Status**: Draft  
**Input**: User description: "データの保存をデータベースではなくファイルにしたい"

## Clarifications

### Session 2026-03-31

- Q: ノートファイルの命名規則は？ → A: UUID＋タイトルの組み合わせ（例: `a1b2c3d4-買い物リスト.json`）。UUIDで一意性を保証し、タイトル部分で人間が識別可能にする。タイトル変更時はファイル名のタイトル部分を更新するが、UUIDで紐付けが維持される。
- Q: JSONファイル内のアイテム構造はフラット配列かネスト構造か？ → A: ネスト構造（子アイテムを `children` 配列で再帰的に格納）。階層が視覚的に明確で、テキストエディタで開いた際に親子関係がインデントで直感的に把握できる。
- Q: 移行完了後の旧データベースファイルの扱いは？ → A: 本番運用前のため移行機能は不要。旧DBは削除してよい。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - データをファイルとして保存・読み込みできる (Priority: P1)

ユーザーがアプリでノートやアイテムを作成・編集すると、そのデータがローカルのファイルに保存される。アプリを再起動しても同じデータが読み込まれ、作業を継続できる。

**Why this priority**: データの永続化はアプリの根幹機能であり、ファイルベースへの移行の核心部分。これなしでは他のストーリーも成立しない。

**Independent Test**: ノートを作成してアプリを終了し、再起動後に同じノートが表示されれば検証完了。

**Acceptance Scenarios**:

1. **Given** 空のアプリ状態で、**When** ノートを作成してアイテムを追加しアプリを終了する、**Then** 再起動後にノートとアイテムが元通りに表示される
2. **Given** 保存済みのノートがある状態で、**When** アイテムの内容を編集する、**Then** その変更がファイルに反映され、再起動後も編集後の内容が保持される
3. **Given** ノートが複数ある状態で、**When** 1つのノートを削除する、**Then** 対応するファイルが削除され、他のノートは影響を受けない

---

### User Story 2 - 保存ファイルをユーザーが直接確認・バックアップできる (Priority: P2)

ユーザーが保存先ディレクトリをOS標準のファイルマネージャーで開くと、ノートごとにファイルが存在し、内容が人間が読める形式で確認できる。ファイルを手動でコピーするだけでバックアップが取れる。

**Why this priority**: ファイルベース移行の主要なユーザー価値。データの透明性とポータビリティがデータベース方式との最大の差別化点。

**Independent Test**: アプリ外でファイルを開き、ノートの内容が読み取れれば検証完了。

**Acceptance Scenarios**:

1. **Given** ノートが保存された状態で、**When** ユーザーが保存ディレクトリをファイルマネージャーで確認する、**Then** ノートごとに1つのファイルが存在し、ファイル名からどのノートか識別できる
2. **Given** ノートファイルが存在する状態で、**When** テキストエディタやJSONビューアでファイルを開く、**Then** ノートのタイトル、アイテム一覧、階層構造が人間が読める形式で確認できる
3. **Given** バックアップとして別の場所にコピーしたノートファイルがある状態で、**When** 元のファイルを削除して復元する、**Then** アプリ再起動後にバックアップのノートが復元される

---

### Edge Cases

- ファイルが外部から削除・破損された場合、アプリはどう振る舞うか？（エラー表示し、他のノートは引き続き利用可能）
- 同一ノートを2つのアプリインスタンスが同時に書き込もうとした場合の競合はどう扱うか？
- ノートのタイトルに`/`や`:` などファイル名に使えない文字が含まれる場合、タイトル部分の禁止文字をサニタイズしてファイル名を生成する（UUIDで一意性は保証されるため、サニタイズによる衝突リスクはない）
- 大量のアイテム（数千件）を持つノートの保存・読み込み速度は許容範囲内か？
- ファイルの読み取り権限がない保存先を指定した場合、ユーザーに適切なエラーが表示されるか？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムはノート・アイテム・アイテムメタデータのすべてを、データベースではなくローカルファイルとして保存しなければならない
- **FR-002**: 1ノートにつき1ファイルを割り当て、ノートに属する全アイテムとメタデータをそのファイル内に格納しなければならない。ファイル名は `{UUID}-{サニタイズ済みタイトル}.json` 形式とし、UUIDで一意性を保証しつつタイトルで人間が識別できるようにする
- **FR-003**: ファイル形式は人間が読み取り可能な構造化テキスト形式（JSON）でなければならない
- **FR-004**: ノート作成・更新・削除の操作は即座にファイルに反映されなければならない（アプリ終了時のまとめ書きは不可）
- **FR-005**: アプリ起動時に保存ディレクトリ内の全ファイルを読み込み、ノート一覧を復元しなければならない
- **FR-006**: ノートを削除すると対応するファイルも削除されなければならない
- **FR-007**: ファイルが外部から削除・破損された場合、該当ノートのみエラーとして扱い、他のノートは引き続き利用できなければならない
- **FR-008**: 旧データベースファイル（`better-sqlite3`）は本番運用前のため移行不要とし、ファイルベース移行時に削除してよい
- **FR-009**: ファイルの保存先ディレクトリはユーザーのデータディレクトリ配下の固定パスとする。v1では変更不可とし、将来の拡張（クラウド同期・外付けドライブ対応）を考慮した設計にとどめる
- **FR-010**: エクスポートスナップショット（履歴記録）はファイルベースへの移行スコープ外とし、この機能のデータ管理方式は別途検討する

### Key Entities

- **ノートファイル**: 1ノートを表す1ファイル。タイトル・説明・表示設定・作成日時・更新日時・バージョンを含む
- **アイテム一覧**: ノートファイル内にネスト構造（`children` 配列による再帰的な親子関係）で格納。各アイテムはID・順序・内容・状態・ハイライトレベル・折りたたみ状態・タイムスタンプを持ち、子アイテムを `children` 配列として内包する
- **アイテムメタデータ**: アイテムに任意付与できる補足情報（目的・カテゴリ・タグ・コンテキストメモ・確信度）。ノートファイル内の対応アイテムに紐付けて格納

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ノートの保存操作（作成・更新）完了後、ユーザーがファイルマネージャーで保存先を確認すると、対応するファイルが1秒以内に存在している
- **SC-002**: アプリ起動時、100ノート・各ノート平均50アイテムの規模のデータを5秒以内に読み込んでノート一覧を表示できる
- **SC-003**: 保存されたノートファイルをテキストエディタで開いたとき、プログラミング知識なしでノートの内容（タイトル・アイテム一覧）が読み取れる
- **SC-004**: ファイルが破損・欠損した状態でアプリを起動しても、他の正常なノートはすべて表示され、エラーが発生したノートのみ「読み込み失敗」として識別できる

## Assumptions

- 本アプリはデスクトップアプリ（Electron）であり、ローカルファイルシステムへの読み書きが常に可能である
- 複数ユーザーが同一の保存ディレクトリを同時に使用するマルチユーザーシナリオはスコープ外とする
- エクスポートスナップショット（`export_snapshots` テーブル相当）はこの機能のスコープ外とし、将来の検討事項とする
- 本アプリは本番運用前のため、旧データベースからのデータ移行は不要。旧DBファイルは削除してよい
- 既存データベースファイルが存在しない新規インストールの場合は移行処理をスキップする
