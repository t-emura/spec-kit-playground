# Feature Specification: Automated Test Pipeline

**Feature Branch**: `002-test-pipeline`  
**Created**: 2026-03-28  
**Status**: Draft  
**Input**: User description: "テスト用のパイプラインを追加したい"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Automated Test Execution on Pull Request (Priority: P1)

開発者として、プルリクエストを作成・更新したときに自動でテストスイートが実行され、結果をPR上で確認したい。これにより、レビュー前に品質問題を早期発見できる。

**Why this priority**: テストパイプラインの中核価値であり、PRごとに品質を自動検証できなければ継続的インテグレーションの目的を達成できないため。

**Independent Test**: PRを作成した際にパイプラインがトリガーされ、全テスト（ユニット・インテグレーション・E2E）が実行され、結果がPR上に表示されることを確認すれば単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 新しいPRが作成された, **When** パイプラインが起動する, **Then** ユニット・インテグレーション・E2Eテストがすべて実行される
2. **Given** テストが完了した, **When** 開発者がPRを確認する, **Then** 各テストスイートのパス/フェイル状態と実行件数が表示される
3. **Given** いずれかのテストが失敗した, **When** パイプラインが終了する, **Then** パイプラインが失敗ステータスで終了し、失敗箇所の詳細が確認できる

---

### User Story 2 - Main Branch Protection via Required Checks (Priority: P2)

開発者として、テストが通過していないPRはmainブランチにマージできないよう保護したい。これにより、壊れたコードがmainに混入するリスクを排除できる。

**Why this priority**: 品質ゲートとしてのパイプラインの信頼性を担保する重要な機能であり、US1が成立した上で意味を持つ。

**Independent Test**: テストが失敗している状態でPRのマージボタンが無効化（またはブロック）されていることを確認できれば単独で検証できる。

**Acceptance Scenarios**:

1. **Given** テストが失敗しているPR, **When** 開発者がマージしようとする, **Then** マージが許可されず、理由が表示される
2. **Given** すべてのテストがパスしたPR, **When** レビューも完了している, **Then** マージが許可される

---

### User Story 3 - Pipeline Execution History and Artifact Retention (Priority: P3)

開発者として、過去のパイプライン実行履歴とテストレポートを参照したい。これにより、品質トレンドの把握や障害発生時の原因調査ができる。

**Why this priority**: 履歴参照は運用上の利便性向上であり、US1・US2が安定した後に価値を発揮するため優先度は低い。

**Independent Test**: 過去の実行一覧からテストレポート（カバレッジ含む）がダウンロード・閲覧できることを確認すれば単独で検証できる。

**Acceptance Scenarios**:

1. **Given** パイプラインが完了した, **When** 開発者が実行履歴を参照する, **Then** テスト結果サマリーとログが保持されている
2. **Given** テストカバレッジレポートが生成された, **When** 開発者がアーティファクトを確認する, **Then** カバレッジレポートがダウンロード可能な状態で保存されている

---

### Edge Cases

- テストが無限ループ・ハングした場合はタイムアウト後にパイプラインを失敗扱いにする
- 外部サービス依存のテストが一時的な接続エラーで失敗した場合、再試行機構でカバーする
- 複数のPRが同時にパイプラインを起動した場合でも、各実行が独立して正しく完了する
- mainブランチへの直接プッシュが行われた場合もパイプラインが実行される

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: パイプラインはPRの作成・更新・mainへの直接プッシュをトリガーとして自動起動しなければならない
- **FR-002**: パイプラインはユニットテスト・インテグレーションテスト・E2Eテストをそれぞれ個別ジョブとして実行しなければならない
- **FR-003**: 各テストジョブの結果（パス件数・フェイル件数・スキップ件数）がPR上に表示されなければならない
- **FR-004**: いずれかのテストジョブが失敗した場合、パイプライン全体を失敗ステータスとして終了しなければならない
- **FR-005**: mainブランチへのマージには、すべてのパイプラインチェックの通過が必須条件として設定されなければならない
- **FR-006**: パイプライン実行は最大30分でタイムアウトし、強制終了しなければならない
- **FR-007**: テストカバレッジレポートはアーティファクトとして保存され、少なくとも30日間参照可能でなければならない
- **FR-008**: パイプラインの実行履歴は少なくとも直近90日間保持されなければならない

### Key Entities

- **Pipeline Run（パイプライン実行）**: 1回のトリガーイベントに対する実行単位。ブランチ名・コミットSHA・トリガー種別・開始/終了日時・最終ステータスを持つ
- **Job（ジョブ）**: パイプライン実行内の個別テストフェーズ（ユニット・インテグレーション・E2E）。独立して実行・結果を持つ
- **Test Report（テストレポート）**: ジョブの実行結果詳細。パス/フェイル/スキップ件数、失敗テストの詳細、カバレッジ情報を含む
- **Artifact（アーティファクト）**: パイプライン実行が生成するファイル（カバレッジレポート等）。保持期間と参照URLを持つ

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: PRへのプッシュから5分以内にパイプラインが起動し、テスト結果がPR上に表示される
- **SC-002**: パイプライン全体の実行時間は平均15分以内で完了する（タイムアウト上限30分）
- **SC-003**: テストが失敗している状態のPRがmainにマージされる事例がゼロになる
- **SC-004**: パイプラインの誤検知（コードに問題がないのに失敗）率が月間5%未満に抑えられる
- **SC-005**: 過去90日間のパイプライン実行履歴とアーティファクトが100%参照可能な状態で保持される

## Assumptions

- 本プロジェクトはGitHub上でホスティングされており、GitHub Actionsをパイプライン基盤として使用する
- 既存のテストスクリプト（`npm test` / `npm run test:unit` / `npm run test:e2e` 相当）がすでに動作する状態にある
- E2EテストはPlaywright、ユニット/インテグレーションテストはVitestで実装済み（既存の実装に基づく仮定）
- テスト実行環境はLinuxベースのCIランナーで動作することを前提とする
- mainブランチへの直接プッシュはチームのワークフロー上でも発生しうるため、パイプラインのトリガー対象に含める
- テストのモバイル・クロスブラウザ対応はスコープ外（デスクトップ環境のみ）
